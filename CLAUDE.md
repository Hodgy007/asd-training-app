# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev              # Start local dev server (localhost:3000)
npm run build            # prisma generate + vitest run + next build
npm run prisma:generate  # Regenerate Prisma client after schema changes
npm run prisma:push      # Push schema changes to the database (no migration file)
npm run prisma:seed      # Seed demo user (tsx prisma/seed.ts)
npm run prisma:studio    # Open Prisma Studio (visual DB browser)
npm run test             # Run Vitest unit tests
npm run test:e2e         # Run Playwright E2E tests
npx tsx prisma/seed-training-content.ts  # Seed training modules/lessons/quizzes into DB
stripe listen --forward-to localhost:3000/api/stripe/webhook   # Forward Stripe webhooks to local dev (requires Stripe CLI)
```

Build runs `prisma generate && cross-env NODE_ENV=test vitest run && next build`. Unit tests (Vitest) run during `npm run build`, so a failing test blocks deployment. E2E tests via Playwright.

## Architecture

Next.js 14 App Router app. TypeScript throughout. Deployed to Vercel (`asd-training-app-v2`); database is PostgreSQL via **Neon** (migrated from Supabase -- Supabase was IPv6-only, incompatible with Vercel Lambda); AI runs through the **Vercel AI Gateway** (AI SDK v6) with a DB-backed prompt registry — default model is `google/gemini-2.5-flash`, but Claude and GPT variants are swappable per-prompt.

**Route groups:**
- `app/(auth)/` -- login, register, forgot-password, reset-password pages; no auth required
- `app/(dashboard)/` -- all leaf-role authenticated pages, wrapped by `app/(dashboard)/layout.tsx` which renders the sidebar + topbar shell; includes `/sessions` (user-facing upcoming/past sessions)
- `app/(super-admin)/` -- super admin pages (`/super-admin/*`), own layout with `SuperAdminSidebar`
- `app/(org-admin)/` -- org admin pages (`/admin/*`), own layout with `OrgAdminSidebar`; includes `/admin/sessions` (session management) and `/admin/settings/meetings` (Zoom/Teams API config)
- `app/(mfa)/` -- `/mfa-setup` and `/mfa-verify` pages for TOTP enrollment and verification
- `app/(change-password)/` -- `/change-password` page for forced password changes
- `app/api/` -- all API routes; auth state is checked via `getServerSession(authOptions)` at the top of each handler
- `app/privacy/` -- public privacy policy page

**Authentication:** NextAuth v4 with `CredentialsProvider` (email + bcrypt password) plus `GoogleProvider` and `AzureADProvider` (registered conditionally when their env credentials are present). The legacy `ENABLE_OAUTH_SSO` env switch is gone — Google + Microsoft are now toggled per-environment by a charity admin in `/super-admin/settings/sso` (single-row `OAuthSsoConfig` model with `googleEnabled` / `microsoftEnabled`). Both default off. The `signIn` callback re-checks the DB toggle so direct hits on `/api/auth/signin/google` are rejected even though the provider is registered. The login page reads `/api/auth/sso-providers` (which queries the same DB row + env-credential presence) to decide whether to render the Google / Microsoft buttons inline above the password form. Uses `strategy: 'jwt'` (JWT sessions, not database sessions). **No PrismaAdapter** -- SSO account linking is handled manually in the `signIn` callback, which checks for an existing `Account` record by `provider + providerAccountId` and creates one if missing. This replaces the previous PrismaAdapter approach and avoids `OAuthAccountNotLinked` errors. The JWT callback extends the token with `id`, `role`, `organisationId`, `mustChangePassword`, `totpEnabled`, `mfaPending`, `hasPassword`, `effectivePrograms` (array of `{ id, name }` objects for the user's resolved training programs), `charityPermissions` (array of permission strings for CHARITY_EMPLOYEE users), and `isParentOrg` (whether the user's org is a parent org); the session callback surfaces all of those onto `session.user`. Unknown OAuth users no longer get an "Account not found" error — they're redirected to `/register/sso-complete` (signed intent JWT with email + provider link) to pick a self-registration role and finish sign-up under the Public Toolkit org. SAML users are still pre-created (or auto-provisioned per-org via `OrgSsoConfig.autoProvision`). Deactivated users (`active: false`) and users in deactivated organisations are blocked at sign-in. The `pendingApproval` login gate has been removed — see the dedicated note below. Session maxAge is set to 8 hours (industry standard for training platforms with sensitive data). Session is accessed on the server via `getServerSession(authOptions)` and on the client via `SessionProvider` in `components/providers/session-provider.tsx`.

**SSO setup (OAuth):** Google + Microsoft OAuth providers are configured app-wide via env credentials. Once `GOOGLE_CLIENT_ID/SECRET` (and/or `AZURE_AD_CLIENT_ID/SECRET/TENANT_ID`) are set on Vercel, the buttons can be turned on per-environment by a super admin at `/super-admin/settings/sso` (UI shows an amber "credentials missing" warning when env vars aren't set, so the toggle can't accidentally be flipped on with no credentials). Redirect URIs to register with each provider:
- Google: `https://asd-training-app-v2.vercel.app/api/auth/callback/google`
- Azure AD: `https://asd-training-app-v2.vercel.app/api/auth/callback/azure-ad`

**Login page:** Email field always visible, debounced (300ms) `/api/auth/sso-check` lookup detects SAML SSO for the email's domain. Three render branches:
1. **Full-screen SSO button** when org SAML SSO matches the typed email, OR when charity SAML SSO is configured with `enforceForCharityUsers=true`.
2. **Optional charity SSO + OAuth buttons + password form** when charity SAML SSO is configured but non-enforced, and/or when OAuth toggles are on. Buttons render inline above the password form with a divider, in this order: charity SSO → Google → Microsoft → "or" divider → password form.
3. **Just the password form** when none of the above apply.

The earlier segmented "Email & Password / Single Sign-On" toggle was removed — auto-detection covers all cases. The `Building2` icon on the SSO badge was swapped for `ShieldCheck` for a clearer security/identity signal. SSO errors from the `error` query param are displayed in the same banner as credentials errors.

**effectivePrograms in session:** The JWT token includes the user's effective training programs (`effectivePrograms`), computed by `lib/modules.ts:getUserPrograms()`. This resolves the user's organisation's `allowedProgramIds` to active `TrainingProgram` records, returning `ProgramInfo[]` (array of `{ id, name }`). This is set on credentials login, SSO login, and session update triggers. The session type is extended in `types/index.ts` to include `effectivePrograms`. The `lib/modules.ts` file exports `getUserPrograms()`, `getOrgPrograms()`, `hasAccess()`, and the `ProgramInfo` interface.

**MFA/TOTP:** SUPER_ADMIN, CHARITY_EMPLOYEE and ORG_ADMIN are all required to enable TOTP MFA (see the `isAdmin` check in `middleware.ts`). Uses the `otpauth` library with `qrcode` for QR display. The middleware enforces MFA in three stages: (1) `mustChangePassword` -- redirect to `/change-password`, (2) `mfaPending` -- redirect to `/mfa-verify` for users with TOTP enabled who haven't verified yet this session, (3) admin roles without TOTP enabled -- redirect to `/mfa-setup` until configured. Login flow for MFA users: password check --> `mfaPending: true` in JWT --> redirect to `/mfa-verify` --> TOTP code submitted via second `signIn()` call with `totpCode` --> `mfaPending: false` --> session active.

**Multi-tenant organisations:** The `Organisation` model supports multi-tenancy. Each org has `allowedProgramIds` (which training programs its users can access), `allowedRoles`, `organisationType` (including `CHARITY` for the charity's own org), contact details (`contactName`, `contactEmail`, `contactPhone`), and address fields (`addressLine1`, `addressLine2`, `city`, `county`, `postcode`, `country`). Users belong to an organisation via `organisationId`. Org admins manage their own org's users, announcements, and reports at `/admin/*`. Super admins manage all organisations at `/super-admin/organisations`.

**Hierarchical organisations (parent/child):** Organisations support a single-level parent/child hierarchy via self-referencing fields: `parentOrgId`, `isParentOrg`, `inheritSettings`, `parentOrg` (relation), `childOrgs[]` (relation). When `isParentOrg` is `true`, the Org Admin sees a "Schools" link in the sidebar at `/admin/schools` where they can create/manage child orgs and their users. Child orgs with `inheritSettings: true` inherit their parent's `allowedProgramIds` and `allowedRoles` (resolved by `lib/org-hierarchy.ts:getEffectiveOrgSettings()`). A parent org's job openings are also visible to its child orgs' learners. All admin APIs (`/api/admin/users`, `/api/admin/reports`, `/api/admin/sessions`, `/api/admin/announcements`) accept `?orgId=` for parent org drill-down, verified by `canManageChildOrg()`. The `isParentOrg` flag is surfaced via JWT to `session.user.isParentOrg` for sidebar rendering. Non-parent orgs are completely unaffected.

**Training programs:** Training is organised into `TrainingProgram` containers, each with a name, description, status (`DRAFT` / `UNDER_REVIEW` / `APPROVED` / `ARCHIVED`), version, and ordered modules. Organisations are assigned programs via `allowedProgramIds`. The `lib/modules.ts` file resolves these to `ProgramInfo[]` objects for the session. The sidebar dynamically renders one nav link per assigned program (e.g. "ASD Awareness Training", "Careers CPD Training") using the program's `name` field.

**Database:** Prisma ORM. Core models:
- `User` -- includes `notificationsLastOpenedAt` (bell badge), `invitedAt`/`invitedBy` (invite audit), `totpSecret`/`totpEnabled`, `charityPermissions[]`, `mustChangePassword`, and a legacy `pendingApproval` column (no longer read or written by the app — the approval gate was removed; column retained so existing rows aren't affected)
- `TrainingProgress` -- per-user completion with `score`, `interactionData` (Json — stores interactive-block interactions), `completedAt`; unique on `(userId, moduleId, lessonId)`
- `Account`, `Session`, `VerificationToken` -- NextAuth tables (Account used for SSO linking; Session and VerificationToken retained in schema but not used by JWT strategy)
- `Organisation` -- multi-tenant org with `allowedProgramIds`, `allowedRoles`, `slug`, `organisationType` (`SCHOOL`/`COLLEGE`/`ACADEMY`/`UNIVERSITY`/`EMPLOYER` + legacy `EDUCATION`/`BUSINESS`), `orgType` (`ORGANISATION`/`COHORT`), `logoUrl`, contact details, address fields, and hierarchy fields (`parentOrgId`, `isParentOrg`, `inheritSettings`, self-referencing `parentOrg`/`childOrgs` via "OrgHierarchy" relation). Has a legacy `pendingApproval` column retained for back-compat but unused by current code.
- `Announcement` -- org-scoped or global announcements with optional expiry
- `TrainingProgram` -- training program container with name, description, order, version, status (`DRAFT` / `UNDER_REVIEW` / `APPROVED` / `ARCHIVED`), review tracking fields
- `Module`, `Lesson`, `QuizQuestion` -- training content CMS; `Module` belongs to a `TrainingProgram` via `programId`. `Lesson` has `type` (`LessonType` enum: `TEXT`/`VIDEO`), `videoUrl`, `transcript`, and `interactiveBlocks` (Json — hotspots, carousels, video blocks; sanitised via `lib/sanitize.ts` using `sanitize-html`)
- `LessonAttachment` -- PDF/image attachments per lesson (shown as "Resources" to learners); uploaded to Vercel Blob
- `LessonNote` -- learner's personal notes per lesson, unique on `(userId, lessonId)`
- `PasswordResetToken` -- forgot-password email flow AND the welcome / magic-link self-registration flow (see "Magic-link self-registration" below). Stored as SHA-256 digest of the raw token; 1h expiry for resets, 24h for welcome links.
- `OAuthSsoConfig` -- single-row toggle for Google + Microsoft OAuth on the login page. Managed at `/super-admin/settings/sso`. Replaces the old `ENABLE_OAUTH_SSO` env flag.
- `ClassSession`, `SessionAttendee` -- virtual classroom sessions (named `ClassSession` to avoid collision with the NextAuth `Session` table; always access via `prisma.classSession`). `ClassSession` has `isCharitySession` flag for charity-level workshops.
- `OrgMeetingConfig` -- per-org Zoom/Teams API credentials and settings for auto-generating meeting links
- `CharityMeetingConfig` -- charity-level meeting API credentials (Zoom/Teams)
- `CharityEventbriteConfig` -- single-row config for the charity's Eventbrite integration. Stores `privateToken` (account-owner OAuth token), `webhookId` (id of the registered webhook subscription so we can revoke on rotate), and `emailMatchPolicy` (`AUTO_INVITE` default / `STRICT` / `CLAIM_LINK`). Token is stored as plaintext to match the existing `CharityMeetingConfig`/`OrgMeetingConfig` pattern; rotate via `/super-admin/settings/eventbrite`.
- `CohortEventbriteEvent` -- 1:1 metadata cache attached to a cohort `Organisation` (where `orgType=COHORT`) sourced from Eventbrite. Cached fields: `name`, `description`, `imageUrl`, `startsAt`, `endsAt`, `venue`, `ticketUrl`, `priceText`, `capacity`, `soldOut`, `status` (`LIVE`/`DRAFT`/`CANCELLED`/`COMPLETED`), `audience` (`EDUCATION`/`EMPLOYER`), `purchasable` (catalogue visibility, default off), `lastSyncedAt`. Refreshed by webhook + nightly cron + manual "Sync now" — never fetched at page-render time.
- `CohortMembership` -- joins `User` to `Organisation` (cohort). Now also carries `source` (`MANUAL` default / `EVENTBRITE`), `externalAttendeeId`, `externalOrderId` so we can correlate cancel/refund webhooks back to a specific row.
- `Survey`, `SurveyQuestion`, `SurveyTarget`, `SurveyResponse`, `SurveyAnswer`, `SurveyInsight` -- complete survey system with targeted audiences, multiple question types (`MULTIPLE_CHOICE`, `YES_NO`, `FREE_TEXT`, `RATING_SCALE`, `MULTI_SELECT`), lifecycle (`DRAFT` / `PUBLISHED` / `CLOSED`), and AI-generated insights (`SUMMARY`, `COMPARATIVE`, `RECOMMENDATIONS`)
- `LibraryCollection`, `LibraryDocument`, `LibraryDocumentEvent` -- document library with collections, file uploads (Vercel Blob), targeted visibility (`targetOrgIds`, `targetRoles`), AI-generated thumbnails, and download/view tracking per user/org
- `JobOpening`, `JobAttachment`, `JobAssignment` -- Jobs feature (managed by charity, consumed by learners). `JobOpening` has employer details, `locationType` (`ONSITE`/`HYBRID`/`REMOTE`), `employmentType` (`INTERNSHIP`/`APPRENTICESHIP`/`PART_TIME`/`FULL_TIME`/`VOLUNTEER`), `status` (`DRAFT`/`PUBLISHED`/`CLOSED`/`ARCHIVED`), `closingDate` (auto-closes past this date), `autismFriendlyNotes`, `skills[]`, `targetOrgIds[]`/`targetRoles[]`. `JobAssignment` is unique on `(jobId, userId)` — CDOs can assign jobs to specific students. See `lib/jobs.ts` for visibility rules + auto-close.
- `AiPrompt`, `AiPromptContextFile` -- DB-backed AI prompt registry. Each prompt has a `key`, `name`, `purpose`, `category`, `tone`, `requirements[]`, `inputVariables[]`, `responseFormat`, `model` (provider/model string), `defaultFields` (Json — fallback seed), `previousFields` (Json — undo). Context files (PDF/DOCX/TXT) are uploaded to Vercel Blob, parsed via `lib/file-parser.ts` (mammoth for DOCX, pdf-parse for PDF), and prepended to prompts.
- `IntegrationApiKey` -- API key management for external integrations (e.g. Power Automate). Keys are SHA-256 hashed (`keyHash`), with a display prefix (`keyPrefix`), expiry, and last-used tracking.
- `OrgSsoConfig` -- per-org SAML SSO configuration with email domain, SSO URL, entity ID, certificate, auto-provisioning, and default role
- `CharitySsoConfig` -- charity-level SAML SSO configuration with enforce-for-charity-users option

Module/Lesson/QuizQuestion cascade on parent delete. Survey/Library/Job/CV cascades on parent delete. The Prisma singleton lives in `lib/prisma.ts`. **The child-observations feature (`Child`, `Observation`, `AiInsight` models and `/children` routes) was removed in commit `8968cf0` — do not reference it.**

**Roles and RBAC:** **Four** roles -- `SUPER_ADMIN` (displayed as "Charity Admin"), `CHARITY_EMPLOYEE`, `ORG_ADMIN`, `LEARNER`. `CAREGIVER`, `CAREER_DEV_OFFICER`, `STUDENT`, `INTERN`, `EMPLOYEE`, `PARTICIPANT` and `FAMILY_CARER` all collapsed into `LEARNER` in July 2026. **Access comes from the training programmes a user's organisation is assigned, not from branching on role** — don't reintroduce role-based feature gating. Internal (charity staff) vs external (schools, companies) is a property of the organisation: the charity has its own `Organisation` row with `organisationType: CHARITY` and its staff are ordinary members. Role helpers live in `lib/rbac.ts`:
- `isSuperAdmin(session)` -- platform-wide charity admin (aliased as `isCharityAdmin`)
- `isCharityEmployee(session)` -- delegated charity-level access with configurable permissions
- `isCharityLevel(session)` -- returns true for SUPER_ADMIN or CHARITY_EMPLOYEE
- `isOrgAdmin(session)` -- manages one organisation
- `isLearner(session)` -- the single end-user role (`isLeafRole` is kept as a deprecated alias)
- `isAdmin(session)` -- backwards-compat alias for `isSuperAdmin`
- `canCreateSessions(session)` -- ORG_ADMIN, or CHARITY_EMPLOYEE with `MANAGE_SESSIONS` permission
- `canManageCharityJobs(session)` -- SUPER_ADMIN, or CHARITY_EMPLOYEE with `MANAGE_JOBS` (charity tier; `canManageJobs` is a deprecated alias)
- `canManageOrgJobs(session, orgId)` -- ORG_ADMIN for their own org, or any charity-level manager
- `canAccessJobs(session)` -- LEARNER (learner-side jobs list)
- `hasPermission(session, permission)` -- permission check; SUPER_ADMIN always returns true, CHARITY_EMPLOYEE checks their `charityPermissions` array, all other roles return false
- `hasRole(session, ...roles)` -- generic role check helper
- `ORG_TYPES` / `ORG_TYPE_LABELS` -- organisation-type constants. `ORG_TYPES` deliberately excludes `CHARITY`: there is exactly one charity org, seeded by `scripts/migrate-to-four-roles.ts`, and it must not be creatable through the provisioning UI.
- `isInternalOrgType(type)` -- true for the charity's own organisation

**Charity permission system:** `CHARITY_PERMISSIONS` defines **ten** permissions: `manage_organisations`, `manage_cohorts`, `manage_training`, `manage_surveys`, `manage_announcements`, `view_reports`, `manage_sessions`, `manage_library`, `manage_ai_prompts`, `manage_jobs`. SUPER_ADMIN has all permissions implicitly. CHARITY_EMPLOYEE users have only those permissions listed in their `charityPermissions` array (stored on the `User` model). The super admin sidebar dynamically shows/hides nav items based on permissions. `PERMISSION_LABELS` provides human-readable labels. `ROLE_LABELS` maps role enums to display names (e.g. `SUPER_ADMIN` -> "Charity Admin"). The RBAC test at `lib/__tests__/` asserts the exact permission count — bump the expected count when adding a permission.

`LEAF_ROLES` in `types/index.ts` is now just `['LEARNER']`. Navigation uses three sidebars: `components/layout/super-admin-sidebar.tsx`, `org-admin-sidebar.tsx`, and `sidebar.tsx` (learners — nothing in it branches on role). The middleware enforces route access: SUPER_ADMIN, CHARITY_EMPLOYEE and ORG_ADMIN cannot access learner routes (`/dashboard`, `/training`, `/careers`, `/settings`, `/guide`), **except** SUPER_ADMIN and CHARITY_EMPLOYEE can access `/training`, `/careers` and `/library` for content preview. (`/guide` is a leftover in that list — the standalone guide routes were replaced by per-page `HowToPanel` components; harmless, but don't take it as evidence the route exists.) `/api/cron` is whitelisted in `PUBLIC_PATHS` for Vercel cron invocations.

**Role home pages:** SUPER_ADMIN --> `/super-admin`, ORG_ADMIN --> `/admin`, LEARNER --> `/dashboard`.

**Super admin training preview:** SUPER_ADMIN can access `/training` and `/careers` pages to preview training content as a learner. The middleware allows this via a `previewPaths` check, and the dashboard layout (`app/(dashboard)/layout.tsx`) bypasses the admin redirect for these paths. The super admin Training Content page (`/super-admin/training`) has a View button (opens training as learner in a new tab) and an Edit button. The lesson editor redirects back to the module page after save.

**Dashboard:** `app/(dashboard)/dashboard/page.tsx` renders one dashboard for every learner — lessons-completed stats, training progress per assigned programme, upcoming workshops, announcements and the Cohort Hub (which no-ops without a cohort membership). The old PARTICIPANT and FAMILY_CARER cut-down variants are gone; they showed a strict subset of this. The page title is "Training Platform".

**Training content (database-driven):** Training content lives in `Module`, `Lesson`, and `QuizQuestion` database tables. Two module types: `ASD` (for practitioners) and `CAREERS` (for career dev officers). Data access layer at `lib/training-db.ts` provides two sets of queries: super-admin queries (include inactive records for editing) and user-facing queries (active records only). Super admins edit content via a WYSIWYG editor (`react-quill-new`) at `/super-admin/training` and can generate quiz questions with AI (Gemini). Seed training data with `npx tsx prisma/seed-training-content.ts`. Progress API is shared: `POST /api/training/progress` accepts any `moduleId`/`lessonId` combination. The `TrainingProgress` model tracks completion per user.

**Sidebar navigation by role:**
- SUPER_ADMIN (Charity Admin): a deliberately short rail — Overview, Feedback, Organisations, **Products**, Reports, Subscribers, Users, then Settings pinned at the bottom. Everything the charity publishes (AI Prompts, Announcements, Brand Assets, Catalogue, Cohorts, Document Library, Home Page, Job Openings, Surveys, Training Content, Workshops) lives behind the **Products** hub at `/super-admin/products`, not in the sidebar. Both the sidebar and the hub tiles filter on `charityPermissions`, and items flagged `charityAdminOnly` (Feedback, Subscribers, Users, Home Page) are hidden from CHARITY_EMPLOYEE entirely.
- ORG_ADMIN: Users pinned first, then everything else sorted with `localeCompare` at render time — Announcements, Billing, Catalogue (opens `/courses` in a new tab), Document Library, Enterprise SSO, Home, Job Openings, Meeting Settings, Reports, [Schools — parent orgs only, falls into its alphabetical slot], Workshops. Settings is pinned at the bottom. Sort in *both* branches if you touch this: it previously sorted only when the org was a parent, so parent and non-parent orgs rendered the same menu in different orders.
- LEARNER: Dashboard pinned first, then everything else sorted alphabetically — [one link per assigned training program from `effectivePrograms`], Document Library (a **single** entry, only when at least one collection is visible), Home, Jobs, Workshops. Settings is in the bottom section above Sign Out. Nothing in `components/layout/sidebar.tsx` branches on role beyond the `role === 'LEARNER'` guard around programmes and Jobs.
- The sidebar container is `overflow-y-auto` so pinned/bottom items stay reachable when the nav is taller than the viewport.

**Dark mode role badges:** All role badges across all admin views (sidebar, org admin user list, super admin org settings) have dark mode color variants using `dark:bg-*/40 dark:text-*-300` patterns.

**Org admin reports:** Reports show proper module names and training plan labels ("ASD Awareness Training", "Careers CPD Training") instead of raw module IDs.

**AI layer:** AI runs through the **Vercel AI Gateway** using AI SDK v6 (`ai` package). All prompts live in the `AiPrompt` DB table (managed via `/super-admin/ai-prompts`, gated by `MANAGE_AI_PROMPTS`). The runtime is `lib/ai-runner.ts:runPrompt(key, values)` — it loads the prompt row by key, assembles it with `lib/ai-runner-assemble.ts` (prepends any uploaded context files), and calls `generateText` against the per-prompt `model` field. Model IDs are provider-prefixed strings defined in `lib/ai-models.ts` (`google/gemini-2.5-flash` — default, `google/gemini-2.5-pro`, `anthropic/claude-sonnet-4`, `anthropic/claude-haiku-4`, `openai/gpt-4o-mini`, `openai/gpt-4.1`). Auth uses `AI_GATEWAY_API_KEY`. All prompts explicitly instruct the model never to diagnose or suggest autism, are strength-focused, and use UK English. Feature-specific callers (`lib/content-generator.ts`, survey insights, quiz generation, library metadata) all delegate to `runPrompt`. On missing prompt rows or errors the runner returns `AI_FEATURE_UNAVAILABLE` — callers must handle that sentinel. **Note:** `lib/gemini.ts` no longer exists — do not reference it. `GEMINI_API_KEY` is still accepted but the canonical path is `AI_GATEWAY_API_KEY`.

**Virtual Classroom Sessions:** Org admins create sessions at `/admin/sessions`. Each session has a title, date/time, duration, platform (Zoom / Teams / Custom), host, and a list of attendees. Attendees can be selected as: all org members, specific roles, or individual users. Both the host and the org admin have full management rights over a session. Meeting links can be pasted manually or auto-generated via the Zoom or Teams API using per-org credentials stored in `OrgMeetingConfig` (configured at `/admin/settings/meetings`). Status flow: `SCHEDULED` → `IN_PROGRESS` → `COMPLETED` (or `CANCELLED`). Attendance is tracked via checkboxes on the `SessionAttendee` join model; a recording URL can be added after the session completes. Users view their upcoming and past sessions at `/sessions`, and the dashboard shows an "Upcoming Sessions" card. Data access helpers live in `lib/sessions.ts`; Zoom/Teams API integration lives in `lib/meetings.ts`. **Important:** the Prisma model is `ClassSession` (not `Session`) to avoid colliding with the NextAuth `Session` table — always use `prisma.classSession`.

**Eventbrite cohorts (external workshop bookings):** Eventbrite events are modelled as cohort `Organisation` rows (`orgType=COHORT`) with a 1:1 `CohortEventbriteEvent` metadata cache. Charity admin pastes a token at `/super-admin/settings/eventbrite`, then pastes an event URL on `/super-admin/cohorts` ("From Eventbrite" button) — we fetch the event details via `lib/eventbrite.ts`, create the cohort + linked metadata via `lib/eventbrite-sync.ts:upsertCohortFromEvent`, and (in production) auto-register a single account-level webhook at `/api/webhooks/eventbrite`. Bookings on Eventbrite fire `order.placed` → we resolve each attendee email per the configured policy and upsert a `CohortMembership` row with `source='EVENTBRITE'`. Three email-match policies: **AUTO_INVITE** (default, recommended) creates a User in the Public Toolkit org and emails a magic-link via `lib/email-templates/workshop-booking.ts` so they can set a password; **STRICT** ignores unknown emails; **CLAIM_LINK** emails a registration link without pre-creating an account. The cohort detail page (`/super-admin/cohorts/[cohortId]`) shows the Eventbrite metadata above the existing tabs (`components/super-admin/cohort-eventbrite-section.tsx`) with a "Show on catalogue" toggle, audience picker, and "Sync now" button. When `purchasable=true`, the workshop appears on `/courses` under "Live workshops" via `components/courses/workshop-card.tsx`. A nightly cron at `/api/cron/eventbrite-sync` (vercel.json, 03:00 UTC) walks every linked cohort and refreshes both metadata and attendee mirror as a backstop. Webhook security: Eventbrite doesn't sign payloads — we trust the request only if `config.webhook_id` matches the id we registered (acts as shared secret) and the `api_url` lives on `eventbriteapi.com`. **Don't recreate a separate "Workshops" admin section** — the cohort IS the workshop in this model.

**Document Library:** Super admins manage document collections at `/super-admin/library`. Each collection has a title, description, optional AI-generated thumbnail, and targeted org/role visibility via `targetOrgIds` and `targetRoles` arrays. Documents are uploaded to Vercel Blob (`@vercel/blob`). Download and view events are tracked per user/org via `LibraryDocumentEvent`. Org admins can view collections at `/admin/library` and edit collection title/description. Users get a single **Document Library** sidebar entry when at least one collection is visible to them; `/library` itself renders the collection grid and drills in (auto-selecting when there's only one). Super admin library reports show download stats per org and per document. AI-assisted metadata generation runs through the AI Gateway via `lib/ai-runner.ts`.

**Surveys:** Super admins create surveys at `/super-admin/surveys`. Each survey has questions (multiple choice, yes/no, free text, rating scale, multi-select), targeted audiences (by org and/or role via `SurveyTarget`), and a lifecycle: `DRAFT` -> `PUBLISHED` -> `CLOSED`. Users see pending surveys on their dashboard and respond at `/surveys/[surveyId]`. AI insights can be generated per survey via `lib/survey-ai.ts` (types: `SUMMARY`, `COMPARATIVE`, `RECOMMENDATIONS`). Survey results are viewable at `/super-admin/surveys/[surveyId]/results`. Survey reports with CSV export are available at `/super-admin/reports`.

**Jobs (two-tier):** `JobOpening.organisationId` decides the tier. **Null** = charity-owned and visible platform-wide, optionally narrowed by `targetOrgIds`; managed at `/super-admin/jobs` by SUPER_ADMIN or `MANAGE_JOBS`-permissioned CHARITY_EMPLOYEEs. **Set** = owned by that organisation, visible only to its learners and to the learners of its child orgs; managed at `/admin/jobs` by its ORG_ADMIN. `organisationId` is deliberately absent from the Zod schemas and set from the session, so a client cannot publish into another org or onto the charity tier by sending null; the `[jobId]` routes check ownership against the job's own `organisationId`, so a charity-tier job is never editable from the org endpoints.

Visibility lives in `lib/jobs.ts` with unit tests. **`targetRoles` is vestigial** — with a single leaf role it cannot narrow anything, and stale values like `['STUDENT']` would otherwise hide live jobs from everyone; the column is retained only so existing rows stay valid. Always build the visibility user via `resolveJobVisibilityUser()` rather than by hand: `parentOrgId` is optional on the type, so a hand-built object silently omits it and child orgs quietly stop seeing their parent's jobs, with no type or runtime error.

**Homepage (per-organisation):** `HomePage` is keyed by `id`, not role. The platform default uses the fixed id `'default'` (see `DEFAULT_HOMEPAGE_ID` in `lib/homepage.ts`); a row with an `organisationId` overrides it for that org's members. The fixed id — not `organisationId` — is what guarantees a single default, because PostgreSQL allows multiple NULLs in a unique index. `resolveHomePage()` falls back to the default, including when an org's page exists but has no blocks; `loadHomePageForEdit()` deliberately does **not** fall back, or saving would copy the default into the org. Editing is charity-only, at `/super-admin/home` with an organisation picker.

**SCORM (packaged lessons):** A lesson with `type = 'SCORM'` hosts a self-contained SCORM 1.2 or 2004 package. The runtime is [`scorm-again`](https://github.com/jcputney/scorm-again) v3 (`Scorm12API` / `Scorm2004API` exposed on `window.API` / `window.API_1484_11`). Key paths:

- **Import**: super admins create a draft program from a SCORM zip via the modal in `components/super-admin/scorm-import-modal.tsx`. Two-stage upload — browser uploads zip to Vercel Blob via a token from `/api/super-admin/training/scorm-import/upload-url`, then `/api/super-admin/training/scorm-import` extracts. Per-lesson upload also works via `/api/super-admin/training/lessons/[lessonId]/scorm`. Max 200 MB. Manifest version detection in `lib/scorm/manifest.ts` (1.2 / 2004 / `CAM 1.3`); zip-slip protection in `lib/scorm/package.ts` walks the central directory before JSZip. Extracted files land under `scorm/<lessonId>/<original/path>` on Blob.
- **Lesson columns**: `scormBlobPrefix`, `scormEntryPath`, `scormVersion`, `scormToc` (Json — parsed `<organization><item>` tree). The TOC is built by walking the default org's items, resolving each `identifierref` to its resource href (querystring from `parameters` is preserved); fallback for legacy single-SCO packages with no organization is the first resource href.
- **Asset serving**: `/api/scorm/[lessonId]/[...path]` is auth-gated, fetches from Blob, and re-emits with a SCORM-specific CSP. The route buffers binary bodies before responding (streaming corrupts media — same gotcha as `/api/tts`).
- **Player**: `components/lessons/scorm-player.tsx` lazy-imports `scorm-again`, instantiates the right API for the version, exposes it as `window[globalKey]`, and listens for `LMSCommit` / `Commit` events to POST CMI to `/api/training/progress/scorm`. Iframe sandbox is `allow-scripts allow-same-origin allow-forms allow-popups` — `allow-same-origin` is required so SCO subresource requests carry the session cookie. The iframe wrapper is `min-h-[600px] h-[70vh]` (not `aspect-video`) and `bg-white` so SCORM content has a proper viewport. **Don't drop `allow-same-origin` without a signed-URL scheme** — subresources will 401 (history: tried it, broke playback, reverted in `c317351`).
- **Multi-SCO TOC sidebar**: when `scormToc` is non-empty, the player renders a left-rail nav that swaps the iframe `src` on click (path-encoded; querystring appended verbatim). The full-width SCORM layout drops the `LessonOutlineRail` since SCORM imports auto-scaffold a single-lesson module — it would just show one row.
- **Resume**: the active TOC leaf href is persisted to `TrainingProgress.interactionData.navLocation` (separate from CMI so it never clobbers a SCO that uses `cmi.core.lesson_location` itself). On mount, the player reads it from `interactionData` and resumes there if it still matches a known leaf. A SCORM Commit fires immediately on each TOC click so the new position is saved before the user can navigate away.
- **Progress mapping**: `lib/scorm/progress.ts:mapScormStateToProgress` accepts both 1.2 and 2004 CMI shapes — completion: `cmi.core.lesson_status` (1.2) ∈ {completed, passed} OR `cmi.completion_status` === 'completed' OR `cmi.success_status` === 'passed'. Score prefers 2004 `cmi.score.scaled` (clamped 0-1, ×100), then raw/max in either location.
- **Quiz analytics**: `lib/scorm/quiz-analytics.ts:aggregateQuizPerformance` walks every CMI snapshot's `cmi.interactions.N.*` keys, groups by question id, and emits `{ attempts, correct, pctCorrect, avgLatencySeconds }`. Sorted ascending so worst-performing questions surface first. Surfaced at `/super-admin/reports/scorm-quizzes` (gated by `VIEW_REPORTS`). Anonymised — never returns per-learner data.
- **CSP gotcha**: client-direct upload to Vercel Blob requires `connect-src` to include `https://vercel.com`, `https://blob.vercel-storage.com`, and `https://*.public.blob.vercel-storage.com` in `next.config.js` — Vercel's blob client SDK calls `vercel.com/api/blob` to coordinate uploads, then PUTs to the storage host.
- **Reports integration**: SCORM completion feeds the standard training reports because `mapScormStateToProgress` writes to `TrainingProgress` like every other lesson type. Score is captured on the column but the cross-org training report only counts completions.

**Training interactive blocks & TTS:** Lessons support inline interactive blocks stored as Json on `Lesson.interactiveBlocks`: hotspot images, carousels (with per-slide TTS), video embeds, and rich-text prose. Block types and sanitisation live in `lib/interactive-blocks.ts` and `lib/sanitize.ts` (sanitize-html — do NOT reintroduce `isomorphic-dompurify` or runtime `jsdom`; `jsdom` is devDependency-only for the Vitest jsdom env). The rich editor is `react-quill-new` with custom image/video formats in `lib/quill-image-format.ts` / `lib/quill-video-format.ts`. A single ElevenLabs TTS player renders above the lesson title for the combined interactive-block text; carousels additionally expose per-slide TTS; prose-only lessons show a bottom player. MP3s are prewarmed on lesson save (`lib/tts-blob.ts`), SHA-256-keyed by `voiceId|text`, persisted to Blob, and streamed (not redirected) through `/api/tts`. Non-audio responses are rejected and MP3 magic bytes are validated. Completion of a Lesson (type `TEXT`) ends in a "Certificate of Completion" with the Ambitious about Autism logo above the heading — template lives in `lib/certificate-template.tsx`. The learner page hides the quiz card when a lesson has no quiz questions.

**Integration API:** External systems (Power BI, Dynamics 365, Power Automate) pull reporting data from `/api/integrations/reports`. Bearer-token auth via `lib/integration-auth.ts` (SHA-256 hashed at rest, 60 req/min per key). Keys managed at `/super-admin/integrations`. Sections: `training | library | surveys | cv | careers | all`. **Two formats:** `?format=nested` (default, v1 back-compat shape) or `?format=flat` (BI-friendly long-format rows with stable `rowId` primary keys). Supports `?since=<ISO>` incremental refresh on event-shaped sections (training is full-population, ignores `since` and surfaces `incrementalSupported: false`), `?limit=` + `?cursor=` cursor pagination on surveys, and weak `ETag` / `If-None-Match` 304. Every response carries `apiVersion: 'v1'` + `generatedAt`. PII pseudonymised via `lib/integration-reports.ts:pseudonymise(userId, namespace)` — partitioned per feature so a leaked CV report can't be cross-referenced against a leaked survey report. Public OpenAPI 3.0 spec at `/api/integrations/reports/schema` for Power BI / Dynamics Custom Connector "Import from URL". **Middleware:** `/api/integrations` is whitelisted in `PUBLIC_PATHS` so Bearer clients aren't redirected to `/login` before the route's own auth runs (this was a latent bug fixed alongside the v2 rewrite). **End-user guide:** `docs/guides/integration-reports-guide.md` covers Power Query, Power BI Desktop / Service, incremental refresh, Dynamics Custom Connector, Power Automate, and per-section column references — keep it in sync when the response shape changes.

**SAML SSO:** Per-org SAML/SSO configuration is stored in `OrgSsoConfig` (fields: `emailDomain`, `ssoUrl`, `entityId`, `certificate`, `autoProvision`, `defaultRole`). Org admins configure SSO at `/admin/settings/sso`. Charity-level SAML SSO is stored in `CharitySsoConfig` with an `enforceForCharityUsers` option. Super admins configure charity SSO at `/super-admin/settings/sso`. The SAML callback is handled at `/api/auth/saml/callback` and login initiation at `/api/auth/saml/login`. SSO check endpoint at `/api/auth/sso-check` determines if a user's email domain has an SSO config.

**Magic-link self-registration:** `/register` `existing-org` and `no-org` paths no longer ask for a password. Submit creates the user with `password=null`, generates a `PasswordResetToken` (24h expiry, SHA-256-hashed at rest, identical infra to forgot-password), and emails a welcome link via Resend (`lib/email-templates/welcome.ts`). Recipient clicks the link, lands on `/welcome?token=…`, picks a password, and is signed in immediately — `/api/auth/welcome` mints a NextAuth JWT session cookie server-side (same pattern as SAML and `/register/sso-complete`). The `new-org` path keeps the inline-password flow because the new ORG_ADMIN needs immediate access. `/register/check-email` is the post-submit confirmation screen for magic-link modes. `/welcome` is in middleware `PUBLIC_PATHS`.

**OAuth self-registration:** When a Google or Microsoft sign-in produces an email that's not in the DB, the `signIn` callback signs a short-lived (10 min) intent JWT carrying `{email, name, provider, providerAccountId}` and redirects to `/register/sso-complete?token=…`. That page asks the same role question as the no-org `/register` path (autistic / parent_carer / supporter / practitioner), then `/api/auth/register/sso-complete` validates the JWT, creates the user under the Public Toolkit org, links the OAuth `Account`, and mints a session cookie. The intent JWT is the only trust boundary — the request body's email/provider are ignored.

**Pending approval removed:** The `pendingApproval` flag on `User` and `Organisation` is no longer read or written. `lib/auth.ts` doesn't gate login on it; `/api/auth/register` creates new orgs and users with `active=true, pendingApproval=false`; the org-admin "Pending Users" tab and the super-admin "Pending Approval" tab are gone; the routes `/api/admin/users/pending` and `/api/super-admin/organisations/pending` are deleted. The columns stay on the schema so existing rows aren't affected — if you want to tidy: `UPDATE "User" SET "pendingApproval" = false WHERE "pendingApproval" = true;` (same for `Organisation`).

## Known Issues / Deployment Notes

- **Vercel 500 on NextAuth routes:** If all `/api/auth/*` routes return 500 after deploy, check that `DATABASE_URL` uses the Neon pooler URL (port 6543) not the direct URL, and that `NEXTAUTH_URL` matches the deployed URL (`https://asd-training-app-v2.vercel.app`) with no trailing slash.
- **Prisma client not found on Vercel:** The build script runs `prisma generate && next build` to ensure the client is always regenerated -- do not separate these.
- **Schema changes:** Run `npx prisma db push` for quick iteration locally. Use `npx prisma migrate dev` if you need a tracked migration file. **Critical:** `.env.local` points to the **dev** Neon branch (`ep-lucky-cherry-a8toqlw5`). To push schema to **production** (`ep-blue-thunder-a88kb0cy`), run `npx vercel env pull .env.production --environment production --yes` then `npx dotenv-cli -e .env.production -- npx prisma db push`. Always push to both dev and production when adding/changing columns that are queried at runtime (e.g. feature flags on Organisation) — otherwise production will crash on queries referencing missing columns.
- **Super admin panel:** Available at `/super-admin`, SUPER_ADMIN role only. Manages organisations, training content, announcements, and platform-wide reports.
- **Org admin panel:** Available at `/admin`, ORG_ADMIN role only. Manages users within their organisation, org-scoped announcements, and org reports.
- **OAuth SSO admin-toggleable:** Google + Microsoft (Azure AD) OAuth providers register with NextAuth whenever their env credentials are set, but the actual sign-in only works when a super admin enables the matching toggle in `/super-admin/settings/sso` (DB-backed `OAuthSsoConfig`). With both toggles off (default) the login page hides the buttons and `signIn` callback rejects any direct provider URL hits. Credentials login and SAML SSO are unaffected by these toggles.
- **SSO Azure AD config:** The Azure app registration must have `signInAudience: AzureADandPersonalMicrosoftAccount` in the manifest to support both personal Microsoft accounts and work/school accounts. Set this in Azure Portal --> App registrations --> Manifest editor. Redirect URI: `https://asd-training-app-v2.vercel.app/api/auth/callback/azure-ad`.
- **SSO Google config:** Google OAuth consent screen must be configured in Google Cloud Console. Redirect URI: `https://asd-training-app-v2.vercel.app/api/auth/callback/google`.
- **SAML SSO users:** Still pre-created (or auto-provisioned per-org via `OrgSsoConfig.autoProvision`). Unknown SAML emails redirect with an error.
- **OAuth SSO users:** Unknown emails are NOT rejected — they're routed through `/register/sso-complete` to self-register. See "OAuth self-registration" above.
- **Forced password change:** Users with `mustChangePassword: true` are redirected to `/change-password` by middleware and cannot access any other route until they change their password.
- **MFA enforcement:** SUPER_ADMIN and ORG_ADMIN users without TOTP enabled are redirected to `/mfa-setup` by middleware and cannot access any other route until MFA is configured.
- **Dev/Prod environments:** Neon database branching is set up. Production uses the main Neon branch; Development uses the `dev` branch (endpoint: `ep-lucky-cherry-a8toqlw5`). Vercel has separate env vars for Production and Development environments. Local dev pulls Development env vars via `npx vercel env pull .env.local`. Git workflow: work on `dev` branch -> merge to `main` -> deploy with `npx vercel --prod --yes`.
- **Vercel Blob:** Document uploads and AI-generated thumbnails use `@vercel/blob`. Requires `BLOB_READ_WRITE_TOKEN` env var.
- **Eventbrite webhook in dev:** `ensureWebhookRegistered` skips webhook registration when `NEXTAUTH_URL` contains `localhost` because Eventbrite can't reach a local box. The cohort-import flow still works in dev — manual "Sync now" + nightly cron cover attendance until prod. In production the webhook auto-registers on the first cohort import.
- **CHARITY_EMPLOYEE role:** Delegated charity-level access. Permissions are configured per-user via the `charityPermissions` array. The super admin sidebar dynamically filters nav items based on these permissions.
- **CSP:** The deployed Content Security Policy allows Google Fonts and `blob:` URLs for media (TTS playback). If you add a new external asset source, update the CSP header in `next.config.js`.
- **In-app how-to panels:** The standalone `/guide` routes are gone. Help is now a collapsed `HowToPanel` at the bottom of each page (`components/howto/panel.tsx`), with the copy in a per-page component under `components/howto/{learner,org-admin,super-admin}/`. Each panel is imported by exactly one page — if you add a panel, wire it up, and if you delete a page, delete its panel. They drift quickly, so update the panel in the same commit as the feature.
- **Preview verification limits:** The `preview_*` tools can't render authenticated routes anonymously — `fetch('/dashboard')` returns `status: 0` because middleware redirects to `/login`. Only `/login`, `/privacy`, and password-reset flows are previewable without a session. For auth-gated pages, rely on type/build checks instead of visual verification.

## Recent Changes

- **Four-role model; CV Builder and Careers Advisor retired; org-level jobs and homepages (July 2026):** Ten roles collapsed into four — `SUPER_ADMIN`, `CHARITY_EMPLOYEE`, `ORG_ADMIN`, `LEARNER`. Access is now driven by an organisation's assigned training programmes rather than by branching on role, and internal vs external is a property of the organisation (the charity has its own org, `organisationType: CHARITY`, with staff as ordinary members). CV Builder and Careers Advisor removed end to end, including their six database tables (all empty on both dev and prod before dropping) — specs and AI prompts preserved in `docs/archive/retired-feature-specs.md`. Jobs became two-tier; homepages moved from role-scoped to org-scoped. Organisation provisioning became a single step (org + programmes + admin + invite). **Breaking:** `/api/integrations/reports` no longer exposes the `cv` or `careers` sections. The `Role` enum change needed a hand-written migration (`scripts/migrate-to-four-roles.ts`) because PostgreSQL cannot drop enum values in place — `prisma db push` would have failed or stranded rows.

- **Integration API v2 for Power BI / Dynamics (May 2026):** `/api/integrations/reports` rewritten to be a usable BI source. Adds `?format=flat` (long-format rows with stable `rowId`), `?since=<ISO>` incremental refresh on event-shaped sections, `?limit=` + `?cursor=` cursor pagination on surveys, weak `ETag` / `If-None-Match` 304, and two new sections (`cv`, `careers`). Every response carries `apiVersion: 'v1'` + `generatedAt`. Fixed two latent bugs: training stats were including cohort orgs (mismatched the in-app super-admin reports) and `/api/integrations` wasn't in middleware `PUBLIC_PATHS` so unauthenticated Bearer calls were being redirected to `/login` before the route's own auth could run. Shared helpers and section fetchers live in `lib/integration-reports.ts`; OpenAPI 3.0 contract at `/api/integrations/reports/schema` (public, no auth) for Custom Connector "Import from URL".

- **Daily per-user caps on AI endpoints (PR #91, May 2026):** Each AI route gained a 24h sliding-window limiter on top of the existing burst limiter, keyed by `session.user.id`, so a stuck client can't run up the Gateway bill. The daily check runs **before** the burst check so the user gets the more meaningful error. 429s on the daily ceiling include `code: 'DAILY_LIMIT'`. The CV Builder and Careers Advisor limiters that shipped in this PR went with those features in July 2026; what remains is training generate-content **20/day** (+10/5min), library doc generate **50/day** (+20/5min), and library collection generate **30/day** (+10/5min). Endpoints added since — home hero-image generate and AI-prompt test — carry a burst limit only.

- **Eventbrite ↔ cohorts integration shipped (May 2026):** Eventbrite events are now a first-class cohort source. Charity admin pastes a token at `/super-admin/settings/eventbrite` (DB-stored, never an env var) then pastes an event URL on `/super-admin/cohorts` → we create a cohort + cached `CohortEventbriteEvent` metadata. Bookings auto-enroll attendees as `CohortMembership` rows via the configured email-match policy (default **AUTO_INVITE** — creates account in Public Toolkit org + sends a workshop-specific magic-link welcome email via `lib/email-templates/workshop-booking.ts`). Eligible cohorts surface on `/courses` as "Live workshops" cards. Webhook (`/api/webhooks/eventbrite`) handles `order.placed/refunded/updated`, `attendee.checked_in/updated`, `event.updated/unpublished`; nightly cron at `/api/cron/eventbrite-sync` is the backstop. There is **no** standalone Workshops admin section — the cohort detail page is the management surface (Eventbrite metadata + Sync button rendered by `components/super-admin/cohort-eventbrite-section.tsx`). Initial design briefly created a `ExternalWorkshop` model + `ClassSession.externalProvider/externalEventId` columns + `SessionAttendee.external*` columns; **all of these were dropped** before merge in favour of the cohort-based model. Don't reintroduce them.

- **Security audit batch landed** (May 2026): twenty-four of twenty-five audit findings merged in a single push (`10232dc`). Highlights to bear in mind for future work:
  - **SCORM entitlement is enforced.** Both the CMI POST (`/api/training/progress/scorm`) and asset GET (`/api/scorm/[lessonId]/[...path]`) now load `lesson.module.programId` and check it against `session.user.effectivePrograms`. If you add another route that touches SCORM data, copy the same pattern. Test mocks must populate `module.programId` and `session.user.effectivePrograms` (see `app/api/training/progress/scorm/__tests__/route.test.ts` for the shape).
  - **Blob downloads are proxied.** Library, training, and job document URLs go through auth-gated `/api/.../download/*` routes — never render raw `*.public.blob.vercel-storage.com` URLs from the server. There is a hash-rewrite migration in `f5b2b19` to back-fill any straggler hrefs.
  - **SVG uploads are blocked.** `lib/upload-validation.ts` keeps SVG in `BLOCKED_EXTENSIONS` because of inline `<script>`/`foreignObject` payloads. If you need admin SVG editing, sanitise via `sanitize-html` before storage. Octet-stream is only accepted for `OCTET_STREAM_OK_EXTENSIONS` (binary formats only).
  - **SCORM zip extraction is hardened.** `lib/scorm/package.ts` caps entry count + decompressed size and parses ZIP64 EOCD properly; manifest path checks reject Windows separators, NFD-encoded traversal, and percent-encoded `..`.
  - **Reset / invite tokens are SHA-256 hashed at rest.** Never compare a raw token against the DB column directly — hash it first via the helper in `lib/tokens.ts`.
  - **CSPRNG everywhere.** All temp-password / token generation uses `crypto.randomBytes`. Don't call `Math.random` for security-relevant strings.
  - **bcrypt cost factor is 12.** Aligned across login, registration, account provisioning, and cohort import. If you add a hashing call-site, match the factor.
  - **AI prompt-test errors are sanitised.** `/api/super-admin/ai-prompts/[id]/test` strips provider-specific stack traces before returning — keep that pattern if you add another admin-facing AI debug surface.
  - **Surveys pseudonymise respondents** with a per-key rate limit so a respondent can't be cross-referenced across surveys.
  - **One audit finding remains unapplied.** SAML admin TOTP enforcement (audit M-24/M-25, patch 0019) is staged in `/tmp/sec-patches/` but not merged — applying it requires every SAML-using admin to have TOTP enrolled first or they'll be locked out. Apply with `git am --3way /tmp/sec-patches/0019-*.patch` once cleared.
